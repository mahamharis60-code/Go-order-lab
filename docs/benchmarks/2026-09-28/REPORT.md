# 云服务器并发与性能验证（2026-09-28）

## 环境与方法

- Ubuntu Linux，2 vCPU，约 3.6 GiB 可见内存（4 GB 规格）；CPU 型号 Xeon Platinum 8255C。
- Go 压测程序与应用运行在同一台服务器，访问 `127.0.0.1:8090`；这是同机回环测试，不是公网客户端压测。
- App、MySQL 8.4、Redis 7.4、RabbitMQ 3.13 使用实际运行的 Docker 容器。服务器上项目二的容器也保持运行。
- 应用镜像 ID：`sha256:ed5837e9d3a1a7a36dc962470b2aa55c779584b508b38506e670798d179ce18c`。
- 下单限流关闭、自动补偿关闭；数据库最大连接 30、最大空闲连接 15，订单 worker 数量 3。
- 压测客户端固定启动 10、20、50、100 个请求 worker goroutine；每个 worker 顺序发送请求。Go HTTP transport 另有内部 goroutine，因此这不是进程总 goroutine 数。
- 闭环负载：一个请求完成后再发下一个，没有思考时间。每档独立准备数据，注册和预热不计入测量。
- 有效下单测试每档 1000 次，每个用户/活动组合唯一且库存充足；订单查询每档持续 30 秒。
- 延迟包含读取完整 HTTP 响应体，分位数采用 nearest-rank；QPS 包括对应场景全部请求。

## 实测结果

| 请求 worker | 有效下单请求 | 受理并落库 | 下单吞吐（单/秒） | 下单 P99（ms） | 查询 QPS | 查询 P99（ms） |
|---:|---:|---:|---:|---:|---:|---:|
| 10 | 1000 | 1000 | 99.26 | 257.62 | 2062.67 | 24.79 |
| 20 | 1000 | 1000 | 126.86 | 244.36 | 2072.53 | 45.79 |
| 50 | 1000 | 1000 | 147.66 | 598.32 | 2068.82 | 91.15 |
| 100 | 1000 | 1000 | 148.12 | 1336.27 | 2067.19 | 181.06 |

四档测试均通过：同一用户 100 次下单仅受理 1 单；200 个用户争抢 30 库存受理 30 单。每档读取持久化订单，确认没有重复用户订单、订单已推进到待支付，并检查初始库存减订单数量等于 MySQL 库存，Redis 与 MySQL 库存一致。对账使用 `repair=false`，没有通过修复库存掩盖失败。

四档合计 253473 次测量请求，传输失败、无效响应和 HTTP 5xx 数为 0。409 业务拒绝单独统计，不视为系统错误。原始 JSON 包含 P50/P95/P99、平均延迟、最大延迟、状态码及业务消息计数。

## 资源与队列采样

以下为整个测试过程的离散采样峰值，不是每个请求的精确资源消耗；CPU 和内存峰值也不保证同一时刻发生。

| 容器 | 采样 CPU 峰值（Docker %） | 内存峰值（MiB） |
|---|---:|---:|
| App | 61.86 | 24.86 |
| MySQL | 50.10 | 527.00 |
| Redis | 5.37 | 10.79 |
| RabbitMQ | 71.45 | 184.80 |

普通订单队列采样到最多 878 条 ready 消息、8 条 unacknowledged 消息。结束时 ready/unacknowledged 均为 0，死信队列为 0。队列采样间隔包含 Docker/RabbitMQ 命令执行耗时，因此可能漏掉瞬时峰值。这证明本次任务最终消化完成，不证明任意故障条件下都能恢复。

另一次使用最终版工具的 100 worker 复测中，1000 次有效下单全部落库，写入批次约 156.72 单/秒、P99 1361.79 ms；写入结束后约 42.50 秒完成所有异步状态和库存核验。该时间包含轮询/API 开销，不能称为纯 MQ 延迟。原始结果见 `recheck-100.json`。

当前 `processOrderCreated` 每条消息包含固定 120 ms 的模拟业务等待。3 个 worker 的理论消费上限在不计算数据库等开销时约为 25 条/秒。因此消息积压受这个人为等待显著影响，不能用它评判 RabbitMQ 本身的性能。本次没有修改该业务行为。

## 如何解释结果

- 从 50 到 100 请求 worker，下单吞吐仅小幅提高，但 P99 从约 598 ms 增至约 1336 ms。增加并发并不必然提高吞吐量，可能主要增加等待。
- 查询约 2 千 QPS 不能表述成下单 2 千 QPS；两条链路的工作量不同。
- 本次有效下单是有限批次，不是长时间稳态写入测试，也不是机器最大容量。尚不能单凭资源快照断言具体瓶颈。
- 同机压测客户端消耗服务器资源，并且没有公网网络延迟；跨机器结果可能不同。
- 本次没有注入 Broker 宕机、死信重放或数据库故障，不提供补偿成功率或故障恢复 SLA。
